# 小模型验证台（Speculative Decoding + 反例搜索）

用 FastAPI + CPU 版 PyTorch 实现的网页应用，包含两个共用同一固定目标模型的工具：

1. **推测解码对照**：验证推测解码能否在保证输出完全一致的前提下节省目标模型的
   前向调用，并验证被拒绝的草稿不会污染后续生成；
2. **反例搜索（新增）**：判断一段 1～32 字符的短提示词，是否会因少量字符替换
   而改变目标模型的下一 token 预测，并按「修改最少、同数字典序最小」给出反例。

所有模型权重在进程内以固定随机种子生成，**无需下载任何模型**；词表为固定的 98 个
字符级 token，草稿与目标模型共用。

## 目录结构

```
app/
  tokenizer.py        固定字符级词表（pad/unk/eos + 95 个可打印 ASCII，共 98 token）
  model.py            带 KV 缓存的小型因果 Transformer + 固定权重的草稿/目标模型；
                      另含无状态外部 KV 前向（反例搜索专用，不触碰模型内部状态）
  decoding.py         无缓存逐 token 贪心基线 与 带 KV 缓存的推测解码
  search.py           反例穷尽搜索（trie DFS 共享前缀 KV + 无缓存整句核对闸门）
  main.py             FastAPI 路由、对照序列化、固定预设、反例搜索接口
static/
  index.html          单页前端（两个标签页：解码对照 / 反例搜索）
tests/
  test_decoding.py       11 项解码关键功能测试
  test_counterexample.py 7 项反例搜索功能测试（含暴力枚举对照与隔离性验证）
Dockerfile / docker-compose.yml  容器化启动
```

## 模型设计（均为固定权重、确定性可复现）

| 模型 | 层数 | 注意力头 | d_model | 说明 |
|---|---|---|---|---|
| 目标模型 | 4 | 4 | 128 | 被核验的大模型 |
| 草稿模型 | 1 | 2 | 128 | 提议草稿的小模型 |

- 二者**共享 token 嵌入与 LM head（权重绑定）**，词表共用；
- 草稿主体在同一初始化 RNG 流之后，再用独立固定种子（seed=99）注入受控高斯扰动
  （σ=0.125）。该尺度经实测使两模型首 token 预测翻转率约 30%，从而同一服务内
  既能稳定观测到**整块接受**，也能稳定观测到**拒绝**；
- 完全独立初始化会导致未训练模型 argmax 近乎 100% 不同（几乎全拒绝），完全一致
  又不会拒绝，受控扰动是让两条路径都可演示的关键。

## 推测解码算法要点

1. 用户设置每轮草稿数 `k ∈ [1,4]`、最多新 token 数 `max_new ∈ [1,32]`；
2. 每轮草稿模型基于**自身 KV 缓存**逐 token 增量写出最多 `k` 个草稿；
3. **目标模型每轮只做 1 次前向**，整块核验草稿；首轮输入「提示词+草稿块」，
   之后每轮输入「上一轮 pending 的纠正/补词 token + 新草稿块」，
   **已缓存前缀绝不重算**；
4. 逐位比对目标贪心预测与草稿 token：
   - 拒绝：丢弃被拒位置及之后的草稿，采用目标在该位置的纠正 token，并把目标/草稿
     KV 缓存截断回滚到接受前缀（回滚无污染，有专项测试）；
   - 整块接受：额外采用目标基于整块上下文的补词 token；
5. `max_new` 上限与 EOS 截断在两条路径上语义完全一致（EOS 计入输出，其后停止）；
6. argmax 平局取词表序号小者（`torch.argmax` 返回首个最大值，天然满足）。

**缓存不变量**：每轮开始时目标缓存覆盖确认前缀倒数第二个 token，pending 保存上一轮
tail；草稿缓存对齐完整确认前缀。因此目标前向次数恒等于推测轮数。

## 正确性保证

推测解码输出在拒绝、整块接受、EOS、达到上限等所有情况下，都与「目标模型**无缓存、
逐 token、对完整前缀重算**的贪心基线」**逐 token 完全相同**。前端在不一致时会标出
首个分歧位置（token id 与文本）并判定 FAIL。

## 反例搜索（工具②）

### 输入与搜索范围

- 提示词：**1～32 个可打印 ASCII 字符**（0x20～0x7E）；
- 在其中 **2～5 个不同位置**各指定 **1～3 个「非原字符」**替换候选；
- 穷尽所有「替换 **0 / 1 / 2** 处位置」的候选（最多替换两处），候选数上界
  C(5,2)×3² = 90（不含原句）；
- 判定对象：目标模型对**下一 token** 的贪心 argmax（平局取词表序号小者）。

### 选择规则

1. **修改位置数最少优先**：先穷尽 1 处替换，未翻转再穷尽 2 处；
2. 修改数相同时，**替换后的完整提示词字典序最小**优先。

找到反例时给出修改前后完整提示词、两处下一 token 预测（id 与字符）、改动位置与
替换字符；全部候选均未翻转时，**仅在完整核对后**报告「所选范围内稳定」。

### KV 复用与互不污染（trie DFS）

所有候选与原提示词构成一棵共享前缀的 trie：DFS 沿树只做单 token 增量前向，
回溯时把 KV 缓存截断回分叉点（末端一个公共 token 重算以取得当前候选 logits），
兄弟分叉之间互不污染。搜索使用模型的**无状态外部缓存**
（`stateless_prefill` / `stateless_next` / `truncate_external_cache`），
模型自身的权重、`_cache`、`cache_len` 与 `forward_count` 完全不被触碰，
因此与推测解码服务可并发共存、互不影响（有专项隔离测试与并发实测）。

### 正确性闸门（失败不发布）

每个候选发布前都与**无缓存整句推理**的 argmax 比对（基线同样核对）；任何计算失败
或缓存/整句预测不一致都会中止搜索并返回错误，**绝不发布反例或稳定结论**。

### 接口

- `POST /api/counterexample`：入参
  `{prompt, edits:[{position, chars:[..1~3 个非原字符]} × 2~5]}`；
  成功返回 `found / baseline / counterexample / stats`，非法入参 400、
  pydantic 越界 422；核对失败 400 且响应体不含任何结论字段。

## 启动方式

### Docker Compose（推荐）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

镜像基于 `python:3.11-slim`，通过 PyTorch 官方 CPU index 安装
`torch==2.5.1+cpu`，不含 CUDA 依赖；带 `/api/health` 健康检查。

### 本地直接运行

```bash
pip install --index-url https://download.pytorch.org/whl/cpu torch
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## 接口

- `GET /api/health`：服务与模型信息；
- `GET /api/presets`：返回固定的「拒绝」「整块接受」两条预设提示词；
- `POST /api/decode`：入参 `{prompt, k(1~4), max_new(1~32)}`，返回两种方式的
  token 序列、解码文本、目标/草稿前向次数、逐轮核验明细、节省统计与一致性判定；
- `POST /api/counterexample`：反例搜索，入参与返回见上一节。

## 实测结果（CPU，torch 2.5.1+cpu，单/双线程）

### 推测解码（`python tests/test_decoding.py`，11 项全部通过）

- 84 组参数组合（7 提示词 × 4 个 k × 3 个 max_new）下，推测解码与贪心基线
  逐 token 完全一致；
- 缓存/无缓存两条前向路径的 argmax 决策逐位相同（logits 仅 ~1e-5 级 float32
  舍入差异）；缓存回滚后续写与整序列前向逐位一致；
- 前向次数（k=4、max_new=32）：
  - 整块接受预设：基线 **32** 次目标前向 → 推测 **7** 次（减少约 78%）；
  - 拒绝预设（首轮接受后持续被拒）：基线 32 次 → 推测 **28** 次，且输出仍与
    基线完全一致，证明被拒草稿未污染后续生成；
- 强制注入 EOS 后，4 个 k × 3 个上限组合下两条路径 EOS 位置与截断完全一致；
- FastAPI TestClient 与真实 `uvicorn` 启动均验证通过，参数越界返回 422、
  空提示词返回 400。

### 反例搜索（`python tests/test_counterexample.py`，7 项全部通过）

- 外部 KV 缓存的分叉/回滚预测与无缓存整句推理逐位一致，兄弟分叉互不污染；
- **40 组随机场景**下搜索结论、最优反例（修改最少、同数字典序最小）与独立
  暴力枚举完全一致；稳定场景的候选核对数等于一级 + 二级候选总数；
- 计算失败与缓存/整句不一致三类故障注入下均抛 `SearchError`、不发布结论；
- 隔离性：搜索前后目标/草稿的权重张量、内部 KV、`forward_count` 不变，
  且再次推测解码的输出与前向次数完全一致；HTTP 并发交错 8 请求实测
  解码输出与搜索结论各自稳定；
- 实测反例（提示词 `3Rs&)d,Nj`，位置 8 的 `j→'`）：下一 token 预测由
  id 77(`j`) 翻转为 id 10(`'`)，1 处修改即命中，搜索在核对第 2 个候选时提前返回；
- TestClient 与真实 `uvicorn` 下：合法请求 200 且结论完整、同字符替换 400、
  位置数越界 422、`/api/health` 不受影响。

> 说明：拒绝预设的前向节省为负向示例——当草稿质量差时推测解码不会节省调用，
> 这正是本验证台要展示的权衡；输出正确性不受影响。
